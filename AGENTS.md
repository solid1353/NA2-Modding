# AGENTS.md

PS2 modding/reverse-engineering workspace for Narutimate Accel v2.28, based on Naruto Shippuuden: Narutimate Accel 2 / SLPS-25837.

## Hard rules

- Use only repository-relative paths in canonical project files, scripts, configuration, logs, manifests, metadata, and generated artifacts; never persist machine-specific absolute paths there. Absolute paths are permitted only in dated `.agents/` handoffs as non-authoritative migration context, transient in-memory command arguments or diagnostic output when a tool requires them, and user-facing clickable file links. Do not persist an absolute path anywhere else unless the user explicitly authorizes that specific exception.
- The task workflow and its plan-approval gate apply only to selected work from `TASKS.md`. Perform small, direct, low-risk changes immediately without a plan, intelligence-level recommendation, or approval gate. Commit and push every completed change automatically; Git operations never require separate user approval.
- For a selected task, only read-only inspection is allowed before plan approval. An unambiguous use of `approved`, `qwe`, or the keyboard-layout equivalent of `qwe` produced by the same physical keys under another active input layout authorizes changes and may appear within a longer message. Agents automatically commit and push their completed changes without approval.
- The user may edit files or create commits while agents are working; treat this as expected concurrent activity, not an anomaly or blocker. Refresh Git status and history before staging, committing, and pushing; preserve concurrent user work and stage only the intended changes unless the user directs otherwise. Agents may push the user's existing commits together with their own. If an agent accidentally includes the user's non-conflicting changes in its own commit, it may push that commit as-is rather than rewriting it; report the inclusion. Pause when concurrent changes directly overlap or conflict with the agent's work, or materially change the requested outcome.
- Concurrent edits to the same file are allowed when their hunks do not overlap, their meanings are independent, and the combined file remains coherent. Use hunk-level staging and commit only the agent's own changes while leaving every other staged or unstaged hunk intact. README and other documentation edits are normally non-exclusive under this rule; pause only when they change the same statement, encode incompatible conclusions, or otherwise create a logical conflict.
- Agents may work concurrently when their tasks and resources are independent. Shared Current/Previous/Candidate promotion state, Git transactions, overlapping canonical edits, physical game input, and any other unisolated mutable resource remain exclusive: the task already using one keeps it, and a competitor uses the bounded sleep/wakeup policy rather than taking it over or inventing substitute work. Worker-output ISO builds and verified agent PCSX2 instances are not exclusive when they use different task-owned paths; PCSX2 launchers serialize only their short shared-configuration injection/restore section, then operate solely through their recorded PID, validated window handle, and PINE port.
- Commit and push every completed change automatically without `qwe` or any other Git approval, using the authoring agent's identity. This applies to implementation, scripts, configuration, data, documentation, `AGENTS.md`, `TASKS.md`, plans, handoffs, cleanup, and selected-task results. Commit at a coherent safe boundary as soon as the requested change is complete; do not leave completed agent work uncommitted for later approval or batching. Preserve concurrent work and stage only the intended paths. A push may include any already-present local commits; do not exclude or rewrite them.
- When progress depends on another task, user action, or external process and no necessary in-scope work remains, stop the active turn instead of busy-waiting, repeatedly polling, or inventing unrelated work. Schedule a thread wakeup at a reasonable interval. Each wakeup performs one bounded status check; if the dependency is still unresolved, make no repository changes, stop again, and schedule the next wakeup. Disable the wakeup as soon as the dependency resolves.
- Use canonical tracked files as shared cross-chat context. Send another chat a concise handoff only when it must act or decide: identify the owner and objective, link exact paths and the relevant commit, state confirmed decisions and unresolved questions, and request the specific next action. Link rather than copy raw logs, command output, or conversation history; do not send acknowledgments, routine status chatter, repeated polls, or duplicate verified analysis beyond cheap drift validation. Keep one owner for each artifact and decision, coordinate before overlapping work, and promote reusable findings into canonical files before signaling dependents.

When the user clearly establishes a recurring workstream rule, the owning coordinator records it without inferred additions and commits/pushes it; do not promote one-off instructions. Current explicit user instructions override stored workstream policy, global rules remain in `AGENTS.md`, and `docs/workstreams/README.md` defines the storage boundary.

Never add inferred constraints, preservation requirements, implementation details, priorities, rationale, files, side effects, or requested actions and present them as user-authorized. Put necessary confirmed facts in a separately labeled `Verified context` section and interpretations or options in a separately labeled non-authoritative section. The recipient treats only the verbatim quotation as the user's instruction. Handle it locally when within scope. Preserve its scope, selected effort, decisions, progress, and approval state; refresh live state and resume from the next incomplete step. `con` does not approve an unapproved plan or bypass a genuine blocker; if no work is resumable, say so.

Preserve the task's scope, decisions, progress, and prior approval state; refresh live state and continue from the safe interruption point without restarting completed work. `sw` is not plan approval.

It overrides the normal continue-working rule: start no new substantive work, reach the next safe boundary without interrupting an atomic write or promotion, preserve restart-critical context and artifacts under the graceful-stop procedure below, release exclusive resources safely, disable pending wakeups unless the user explicitly wants monitoring to continue, and hand control back only when the task is safe to resume later.

Never use another agent's registered identity. Do not change repository or global Git identity, rewrite existing commit subjects, or alter user-authored commits.

Answer or acknowledge them in commentary, never as the turn's final response, and immediately continue executing. ## Task workflow and approval

Before inspecting, planning, or executing a selected task, verify that it belongs
to the current Codex task/chat's workstream and responsibility. If it belongs in
another existing workstream coordinator or dedicated task chat, route it there
immediately with the task text, status, user instructions, relevant context,
and any work already performed; tell the user where it was routed, then stop
handling it in the current chat. Do not duplicate the task across chats. If no
suitable chat exists, send one setup request to `Task coordinator` and follow
the chat-creation approval rules below instead of absorbing the work locally.

A `TASKS.md` task becomes selected only when the user explicitly chooses a
specific listed entry for execution or explicitly instructs the agent to start
that entry. Do not infer selection from topical overlap, the workstream's status,
a task mention, inspection depth, or the amount of work needed to answer.
Questions, explanations, status checks, read-only investigations, coordination
or handoff messages, and small direct changes are not selected tasks. Handle
them without the task phase block, `Recommended effort`, `Needed from you`, or
an approval gate unless the user explicitly sends `eff`. If intent is ambiguous,
answer or investigate read-only as requested; do not silently convert the
interaction into selected-task execution.

Read-only inspection for a selected task may begin immediately without plan
approval. At the start of any inspection that may take more than a brief check,
the agent must provide this status block before or with its first inspection
action:

```text
Phase: read-only inspection
Purpose: gather enough evidence for the plan
Changes: none
Recommended effort: <level>
Next response: short plan + effort recommendation + needed user inputs + approval gate
```

The initial effort recommendation is provisional and must be stated even when
inspection is still needed. If the evidence changes the recommendation, explain
the change in the plan. Progress updates during a long inspection must keep the
current phase and required next response clear.

Assess effort independently for the current work instead of inheriting the
chat's previous level, copying historical recommendations, or defaulting to the
highest available level. Consider the actual reasoning depth, uncertainty,
reverse-engineering breadth, cross-component coupling, consequence of error,
reversibility, and validation burden, then recommend the lowest level likely to
produce a reliable result. The brief justification must name the decisive
task-specific factors. Repeating a prior level is correct only when this
assessment supports it; changing levels merely for variety is also incorrect.
Reassess when inspection materially changes those factors, not at every status
update.

Until a selected task is completed, every final response that hands control
back to the user must include a standalone `Recommended effort: <level>` line.
This applies after inspection, at approval gates, in execution handoffs, and at
every stop, pause, dependency, safety, or relaunch boundary. Stating the level
only in commentary or an earlier response does not satisfy this requirement; if
the recommendation changes, explain why.

Reporting the selected task complete ends its selected-task state immediately;
this does not depend on the user later removing its entry from `TASKS.md`.
Subsequent questions, explanations, status checks, and small direct changes use
the normal non-task response format without `Recommended effort`, `Needed from
you`, or an approval gate unless the user selects another task or sends `eff`.
Never carry task-phase boilerplate forward merely because the completed entry
still exists in `TASKS.md`.

Every selected-task plan must include a standalone `Needed from you: <items>`
line beside `Recommended effort`. Ask specifically for every user-supplied input
or action that is expected or may materially help execution, such as savestates
at named screens, screenshots, files, test results, tool access, or an in-game
action. Request the ideal decision-quality inputs up front rather than convenient
low-value proxies; when relevant, specify the exact game state, screen, timing,
version, configuration, and reproduction conditions that must match. Explain
when and why each item is needed. Use fallback evidence only when the ideal input
is unavailable or impractical, and state the resulting limitation and whether
the conclusion remains provisional. If the agent needs nothing from the user,
state `Needed from you: nothing` instead of omitting the line.

### `zxc` graceful stop and resume

- On `zxc`, acknowledge the command and stop at the next safe boundary. Do not begin another investigation, test, build, launch, refactor, cleanup pass, commit of incomplete implementation, or unrelated task. Do not abruptly interrupt an atomic file operation, Git operation, ISO promotion, or other action whose interruption could corrupt state; finish or cancel it only through its supported safe path.
- Create a dated `.agents/<date>-<task-title>-resume.md` handoff before stopping. Record the exact objective and task wording; task/chat title; current phase, plan, effort recommendation, and approval state; completed and remaining steps; decisions and user corrections; commands, results, and tests; Git HEAD/status plus owned staged and unstaged paths; files read and modified; the owned `work/<task title>/` directory and every retained artifact; running processes and exclusive resources; required user inputs; uncertainties; and the exact first action on resume. Never rely on chat memory or in-memory process state as the only copy of restart-critical context.
- Preserve the minimum files needed to resume without repeating expensive work. Do not perform normal end-of-task cleanup during a graceful stop; retain useful partial outputs and identify them in the handoff. Remove or abandon a temporary file only when it is confirmed disposable and doing so cannot harm resumption. Safely close agent-launched PCSX2 and release other exclusive resources when possible; otherwise record their exact state and why they could not be released.
- Commit and push only the documentation handoff automatically. Do not stage or commit incomplete implementation merely because `zxc` was issued, and preserve all concurrent user or agent work. The final response must identify the handoff, say whether restart/reboot is safe, list any remaining live operation or hazard, and include the required standalone effort recommendation when a selected task remains incomplete.

## Build and launch workflow

The root command interface is: bare `na2` builds, conditionally rotates, and launches Current; `na2 -b` runs that standard pipeline without launching; bare `na2 -t` fully rebuilds shared Candidate without PCSX2, promotion, rotation, or preflight mutation; `na2 -t work/<task title>/build/<name>.iso` performs the same full verification with task-owned output and logs; `na2 -c` and `na2 -p` are pure Current/Previous launch selectors; and `na2 act` maintains PNACH aliases. Routine builds and launches never change PNACH aliases. Source-game shortcuts remain in the user's PowerShell profile. `_na2.ps1` owns dispatch/transcripts, `scripts/na2/build.ps1` owns the three build modes, `na2_patcher` composes and verifies the image, and `scripts/na2/launch.ps1` only starts PCSX2; do not recombine these responsibilities.

During on-demand PNACH maintenance, keep the canonical file named `@pcsx2_files/SLPS-25837_C0659AD1.pnach`. Managed aliases are only matching-serial symlinks that resolve to this canonical file; preserve all real PNACH files, other games, and unrelated symlinks. If the canonical file is zero bytes, delete its managed aliases directly and skip ISO/CRC inspection. Otherwise, calculate the PCSX2-style ELF CRC from the Current and Previous ISOs as applicable, delete obsolete managed aliases, and create the required CRC-named relative symlinks targeting the canonical project PNACH. Refuse an occupied target filename instead of overwriting an unmanaged file or symlink.

Use `na2 act` only when preparing a non-empty PNACH for runtime testing, after an ISO change may have changed the boot ELF CRC, or to remove managed aliases after emptying the canonical PNACH. Editing a canonical PNACH through an existing valid symlink needs no re-actualization.

User-owned standard builds may close the configured PCSX2 process as required by promotion. Bare Candidate and explicit worker-output builds never probe or close PCSX2. Agent runtime testing never performs a name-wide close and may stop only its recorded PID after validating the executable and process start time.

Agents share the PCSX2 executable, BIOS, resources, profiles, and other confirmed read-only inputs. Before launch, `test_launch.ps1` briefly locks the shared configuration, redirects writable folders into `work/<task title>/`, selects a task-owned card copied from the effective base card, assigns a free PINE port, and launches hidden/muted. After PINE reports the expected serial/CRC—proving per-game settings loaded—the wrapper restores shared settings immediately and releases the lock; exit-time restoration is guarded so it cannot overwrite unrelated changes.

Agent PCSX2 testing must use `scripts/na2/test_launch.ps1 -WorkerRoot work/<task title>`. The wrapper records a portable instance descriptor containing PID, process start time, PID-validated top-level window handle, ISO identity, private card, worker paths, and unique PINE port. Every hide/focus/observation/close operation targets that instance only; never enumerate or manipulate other PCSX2 windows. Mutable logs, savestates, screenshots, recordings, cards, cache, and dump outputs are task-owned, while shared replacement textures remain read-only. Launch running by default; use the wrapper's `-StartPaused` option when a test requires a paused initial state. Never implement task-local direct rewrites of shared PCSX2 settings, including `StartPaused`; extend or reuse the maintained guarded runtime configuration instead. Close every agent-launched instance when unneeded, delete its descriptor and disposable runtime data, and retain useful task artifacts under `inputs/` or `artifacts/` with documentation.
